# 녹음본 피드백 시스템 설계

> **For**: 피드백 시스템을 만들 사람 (개발자·AI). 작성자에게 되묻지 않고 계획을 세울 수 있어야 한다.
> **You'll be able to**: 공연 단계·녹음본 제출·피드백 입력·점수 계산·결과 발표·셋리스트까지 무엇을 어떻게 만들지 안다.

입력: [피드백 시스템 요구사항](feedback-system-requirements.md)(26-여름 2차 회의 + 32기 스크립트) · 운영진 인터뷰 2건(2026-10) · 개발자 초안(2026-10-30). 작업 추적: [#898](https://github.com/skku-amang/main/issues/898). 용어는 [용어집](../../reference/glossary.md)을 따른다.

## 1. 왜 만드나

지금 녹음본 피드백은 **구글 폼으로 받고 → CSV를 내려 → 파이썬 스크립트로 집계 → 결과를 손으로 옮긴다**. 간부진: "피드백만 해도 2시간". 운영진 인터뷰 2명 모두 홈페이지에 가장 먼저 생겼으면 하는 기능으로 꼽았다. 홈페이지 한 곳에서 제출·피드백·집계·발표까지 끝내는 것이 목표다.

## 2. 목표 · 비목표 · 안티목표

**목표 (v0.1)**

- 운영진이 공연 날짜 몇 개만 넣으면 단계가 저절로 바뀌고, 그 단계에 맞는 행동만 열린다.
- 팀은 홈페이지에 녹음본을 올리고, 부원은 홈페이지에서 피드백을 남긴다.
- 점수 계산은 32기 스크립트와 **같은 결과**를 낸다. 운영진이 계산 과정을 보고 확정한다.
- 확정하면 전원에게 알림이 가고, 결과 페이지에서 합불을 확인한다. 운영진은 셋리스트를 짠다.

**비목표**

- 산정식 변경 (D8 — 검증된 로직 그대로. 바꾸려면 간부진 합의)
- 영상 파일 업로드 (음원만. 영상은 용량·재생 문제가 별개)
- 연합 공연·방학 공연의 다른 참여 정책 ([요구사항 5절](feedback-system-requirements.md#5-범위-밖-기록만))
- 단계 전이·운영진 조작의 이력 기록 (자동 전이는 날짜를 보면 알 수 있고, 수동 조작은 API 로그로 충분. 사고가 나면 그때)
- 이메일 등 새 알림 채널
- 공연별 피드백 문항·가중치 설정 (백로그. 5.2절의 확장 경로)

**안티목표 — 이러면 만들어도 실패**

- 계산 결과가 스크립트와 달라 운영진이 구글 폼으로 돌아간다.
- 피드백 기간에 팀원이 누군지 보인다 (곡 위주 평가 원칙 훼손).
- 어느 부원이 어떤 점수를 줬는지 팀에게 드러난다.
- 날짜 하나 잘못 넣었는데 운영진이 못 고쳐 단계가 멈춘다.

## 3. 제약

- 1인 개발 + AI. 작은 단위로 끊어 배포한다 (하위 이슈 순서 = 배포 순서).
- 기존 스택 그대로: Prisma · NestJS · Next.js · `@repo/shared-types`(Zod) · MinIO 업로드([upload 모듈](../../../apps/api/src/upload/)) · 알림 시스템([#347](https://github.com/skku-amang/main/issues/347), [reminder 스케줄러](../../../apps/api/src/reminder/) 10분 주기).
- **지금 `Performance.endAt`(공연 종료 일시)이 모집 마감 역할을 겸한다** — [`isPerformanceRecruiting`](../../../packages/shared-types/src/performance/performance.types.ts). 호출처: team.service 지원 차단, reminder 모집 마감 D-1, web `lib/performance.ts` D-day·목록 분리. 새 날짜 필드로 **한 PR에서 전부 교체**한다 (반쪽 교체 시 지원 가능 여부가 화면·서버에서 어긋남).

## 4. 공연 단계

### 4.1 단계 7개

| 단계      | 코드         | 뜻                       | 열리는 것                                | 잠기는 것                       |
| --------- | ------------ | ------------------------ | ---------------------------------------- | ------------------------------- |
| 준비      | `PREPARING`  | 공연 만들고 날짜 넣는 중 | 운영진 편집                              | 팀 생성·지원                    |
| 팀 모집   | `RECRUITING` | 팀 만들고 지원           | 팀 생성·지원·탈퇴, 녹음본·사진·설명 등록 | —                               |
| 제출      | `SUBMISSION` | 팀 확정, 녹음본 마감 전  | 녹음본·사진·설명·곡 정보 수정            | 사람 변경 (4.4절)               |
| 피드백    | `EVALUATION` | 상호 피드백              | 피드백 입력·수정                         | 팀의 모든 것, **팀원 가림**     |
| 집계      | `DECISION`   | 운영진이 계산 확인       | 운영진 확정                              | 피드백 입력, **팀원 가림 유지** |
| 공연 준비 | `LINEUP`     | 결과 공개, 셋리스트      | 결과 페이지, 운영진 셋리스트 편집        | —                               |
| 종료      | `DONE`       | 공연 끝                  | 열람만                                   | 전부                            |

용어집의 6단계에 `LINEUP`을 추가했다 → [용어집](../../reference/glossary.md#공연-라이프사이클-7단계) 갱신 포함.

### 4.2 단계는 저장하지 않고 날짜에서 계산한다

`Performance`에 날짜를 두고, 단계는 **읽을 때 계산**한다. cron이 단계를 바꾸지 않고, 수동 개입은 날짜를 고치는 것이다. (지금 `isPerformanceRecruiting`이 이미 이 방식.)

```text
Performance 새 필드
  recruitStartAt   DateTime?   모집 시작
  recruitEndAt     DateTime?   모집 종료 (= 팀 구성 잠금)
  feedbackStartAt  DateTime?   피드백 시작 (= 녹음본 제출 마감)
  feedbackEndAt    DateTime?   피드백 종료
  decidedAt        DateTime?   운영진 확정 시각
  passCount        Int?        합격 곡 수 (스크립트 N_PASS)
  penaltyPerMissingReview Float @default(0)   미참여 1건당 감점 (5.4절)
기존 startAt / endAt = 공연 자체의 일시 (의미 복원)
```

```text
stage(performance, now):
  if endAt && now >= endAt              → DONE
  if decidedAt                          → LINEUP
  if feedbackEndAt && now >= feedbackEndAt   → DECISION
  if feedbackStartAt && now >= feedbackStartAt → EVALUATION
  if recruitEndAt && now >= recruitEndAt     → SUBMISSION
  if recruitStartAt && now >= recruitStartAt → RECRUITING
  else                                  → PREPARING
```

- 날짜가 비어 있으면 그 단계로 못 넘어간다. 단 공연 종료가 지나면 무조건 `DONE` (옛 공연 처리).
- `recruitEndAt == feedbackStartAt`이면 제출 단계는 건너뛴다 (운영진이 원하면 생략).
- 이 함수는 `@repo/shared-types`에 한 번만 두고 서버·웹이 같이 쓴다 (`isPerformanceRecruiting` 교체).
- **마이그레이션**: 기존 공연은 `recruitStartAt = createdAt`, `recruitEndAt = endAt`으로 채운다 → 현재 동작("공연 종료까지 지원 가능")과 같아진다.

### 4.3 운영진 수동 개입

운영진은 공연 관리 화면에서 날짜를 고치거나 "지금 시작/마감" 버튼(= 해당 날짜를 지금으로)을 누른다. 확정은 `decidedAt`을 찍고, 되돌리기는 지운다. 별도 이력 테이블은 두지 않는다 — 날짜가 편집 가능하면 안티목표("못 고쳐 멈춤")는 해결되고, 누가 언제 바꿨는지는 API 요청 로그로 보존 기간 안에서 추적된다. 사고가 실제로 나면 그때 추가한다.

### 4.4 팀 소속자, 잠금 범위, 고정팀 권한

- **팀 소속자 = 팀장(`Team.leaderId`) ∪ 세션 멤버(`TeamMember`)**. 코드상 팀장은 세션 자리 없이도 팀장일 수 있다. 이 문서의 피드백 자격·본인 팀 제외·진행률 분모·감점 건수·팀원 가림·알림 수신자는 모두 이 기준이다 ([알림 설계](notification-system-design.md)와 같음).
- **제출 단계 잠금**: 사람에 관한 것은 전부 잠긴다 — 세션 멤버 추가·제거·탈퇴, 세션 정원, 팀장 교체, 팀 삭제. 허용: 곡 정보(제목·아티스트·자작곡 여부), 팀 이름, 설명, 사진, 녹음본. 피드백 단계부터는 전부 잠긴다. 그만두는 팀은 녹음본을 올리지 않으면 미제출로 처리된다. (`PUT /teams/:id`가 팀을 통째로 교체하는 구조라, 필드별 검증으로 쪼갤지 녹음본·설명 전용 엔드포인트를 둘지는 빌더가 정한다.)
- **`isFreshmenFixed`는 운영진만 설정한다.** 지금은 팀 폼에서 누구나 체크할 수 있어 합격 보장 구멍이다. 팀 생성·수정 폼에서 체커를 빼고, 서버는 운영진이 아닌 사용자의 변경을 거부한다. 운영진은 공연 관리 화면의 팀 목록에서 토글한다. 기존 값은 그대로 둔다.

## 5. 단계별 동작

### 5.1 녹음본 제출 (모집~제출)

- `Team.recordingUrl String?` 추가 — 기존 `image`처럼 MinIO 공개 URL 전체를 저장한다. 기존 presigned 업로드 경로 재사용, 객체 키는 추측 불가능한 랜덤값. 버킷이 공개 읽기라 링크를 아는 사람은 로그인 없이 재생할 수 있는데, **사진과 같은 공개 수준으로 두기로 결정**했다 (커버곡 연습 음원, 유출 피해 작음. presigned GET·별도 버킷 정책 안 함). 음원만 (`audio/*`). 기존 `image`(대표 사진)·`description`(설명)이 "대표 사진과 짧은 설명글"에 해당.
- 올릴 수 있는 사람: 팀장. 기간: 팀이 생긴 때부터 `feedbackStartAt` 전까지.
- `songYoutubeVideoUrl`은 건드리지 않는다 (피드백과 무관한 기존 필드).
- **피드백 시작 시점에 녹음본이 없는 팀은 피드백 대상에서 자동 제외**된다. 평가받지 않고 불합격 처리, 결과 페이지에 "미제출"로 표시. 운영진은 제출 단계 화면에서 미제출 팀 목록을 본다.
- "피드백 대상 팀(pool)" = 그 공연 팀 중 `recordingUrl != null`. 피드백 단계부터 잠겨 있으므로 저장 없이 계산한다.

### 5.2 피드백 입력 (피드백 단계)

```text
Feedback
  id, teamId, reviewerId, createdAt, updatedAt
  teamScore        Int   팀 완성도
  individualScore  Int   개인 완성도
  preferenceScore  Int   선호도
  comment          String?   점수와 무관한 자유 의견
  @@unique([teamId, reviewerId])
```

- **문항은 32기 스크립트 그대로**: 팀 완성도·개인 완성도·선호도 + 자유 의견 ([요구사항 3절](feedback-system-requirements.md#3-현행-점수-산정-로직-32기-스크립트-분석)). 점수 범위는 1~5 (8절, 운영진 확인은 7절).
- **문항은 고정이다** (공연별로 바꾸지 않음). 몇 년간 바뀐 적이 없고, 바뀌면 가중치·산정식도 함께 바뀌어 간부진 합의(D8)가 필요하므로 코드 변경이 맞는 게이트다. 대신 `@repo/shared-types`에 `FEEDBACK_DIMENSIONS = [{ key, label, weight }]` 상수 하나를 두고 폼·계산·집계 화면이 전부 이 배열을 돌린다 — "3"이 코드에 박히지 않는다. 공연별 문항이 필요해지면 이 상수를 테이블로 옮기는 것이 확장 경로다 (백로그).
- **자격**: 피드백 대상 팀 중 하나 이상의 소속자 (팀장 포함, 4.4절). 팀 없는 회원·미제출 팀만의 소속자는 입력 불가.
- **본인 팀 제외**: 자기가 속한 팀은 목록에서 빠진다 (D1 — 스크립트의 "본인 곡 0점" 관례 폐기).
- 피드백 단계 안에서는 몇 번이든 수정 가능. 단계 밖에서는 서버가 거부.
- **팀원 가림**: `EVALUATION`·`DECISION` 동안 운영진이 아닌 사용자에게는 **소속자 전부**(팀장 포함)를 숨긴다. 적용 범위: 팀 상세·목록 API(세션별 배정과 `leader`), 팀 목록 화면의 팀장 칩, 그리고 **프로필 API의 `leadingTeams`·`joinedTeams`**(그 공연의 팀은 빼고 응답 — 안 가리면 여기로 샌다). 곡 정보·녹음본·사진·설명만 보인다. 공연·팀 조회 API가 `@Public`이라 **비로그인 사용자에게도 같은 가림**을 적용한다. 이 규칙은 [동아리 운영 모델](../club-operations.md)에도 운영 규칙으로 적는다.
- 피드백 작성자는 팀에게 익명이다. 운영진은 누가 썼는지 본다 (지금 구글 폼 시트와 같음).

### 5.3 미참여 확인 (피드백~집계)

- 작성자별 진행률 = 입력한 팀 수 / (대상 팀 수 − 본인 팀 수). 운영진 화면에 팀별로 "미완료 소속자"를 보여준다 (R2).
- 미완료 작성자에게 마감 알림 (6절).

### 5.4 집계와 확정 (집계 단계)

계산은 **[32기 스크립트](feedback-system-requirements.md#부록-a--32기-점수-산정-스크립트-원본)를 TypeScript로 그대로 옮긴다** (D8). 서버에서 계산하고 결과를 저장하지 않는다 (입력이 잠겨 있어 항상 같은 값).

1. 작성자마다, 본인이 점수를 준 팀들만으로 문항별 평균·표준편차 → z-score. 표준편차 0이면 전부 0.
2. 팀·문항별 점수 = z-score 합 ÷ 그 팀에 점수를 준 작성자 수. (스크립트의 "전체 − 참여자" 분모는 전원 제출을 가정했다. 여기서는 **실제로 점수를 준 사람 수**로 나눈다 — D2. 전원 제출이면 같은 값.)
3. 가중합 = 2×팀 완성도 + 2×개인 완성도 + 1×선호도.
4. **감점 (R3, Pay-to-vote 팀 단위)**: 가중합 − `penaltyPerMissingReview` × (그 팀 소속자들이 안 쓴 피드백 건수). 한 사람이 여러 대상 팀에 속하면 그 사람의 미작성 건수는 소속 팀마다 반영된다. 기본값 0 = 감점 없음. 수치는 운영진이 공연마다 넣는다 (7절).
5. 내림차순 상위 `passCount` 합격.
6. **신입 고정곡 보장 (D4)**: 합격권 밖의 `isFreshmenFixed` 팀(운영진만 설정, 4.4절) 수만큼 합격 목록 끝을 빼고 고정 팀을 넣는다. 미제출 고정팀은 대상이 아니므로 보장도 없다.
7. 부산물: 합격·불합격 팀, 합격 팀 소속자 전체 = 공연 참가자 (R7).

운영진 화면(`/admin/performances/[id]/feedback`)은 이 과정을 **단계별로 보여준다**: 참여 현황 → 작성자별 원점수와 z-score 표 → 팀별 문항 점수·가중합·감점 → 순위와 합격선 → 고정곡 삽입 전/후. 신입 고정팀은 따로 묶어 표시 (R5). 맨 아래 "확정" 버튼 → `decidedAt` 기록 + 알림. 되돌리기는 `decidedAt`을 지운다 (운영진만).

**완료 기준**: 지난 공연 구글 폼 CSV를 변환해 넣었을 때 스크립트와 같은 순위·합격 목록이 나오는 테스트가 있어야 한다. 전제는 **전원 제출 CSV**(또는 미제출 작성자 행을 지운 CSV)다. D1·D2 때문에 미제출·부분 제출이 섞이면 값이 달라지는 것이 설계상 정상이고, 스크립트 분모 방식으로 되돌리는 스위치는 두지 않는다. 변환할 때 "전 문항 0점 = 본인 팀" 관례로 소속을 역산한다. CSV는 간부진에게 받는다 (7절).

### 5.5 결과 공개와 셋리스트 (공연 준비 단계)

- 결과 페이지 `/performances/[id]/result`: 합격 팀 목록 (신입 고정팀 구분), 불합격 팀, 미제출 팀. 로그인한 부원은 **본인 팀**의 순위·점수·받은 자유 의견(작성자 익명)을 본다. 운영진은 전부 본다. 알림을 누르면 이 페이지로 온다. 결과 페이지와 피드백 페이지(`/performances/[id]/feedback`)는 **로그인 필수** — [proxy.ts](../../../apps/web/proxy.ts) matcher에 추가. 기대감을 갖고 여는 페이지라 간단한 공개 애니메이션을 둔다 (구현은 빌더).
- 셋리스트: `Team.lineupOrder Int?`, `Team.lineupPart Int?`(1부/2부). 운영진 화면 `/admin/performances/[id]/lineup`에서 합격 팀을 드래그 앤 드롭으로 정렬하고 1·2부 경계를 끌어 나눈다. 공연 상세 페이지는 `LINEUP`·`DONE`에서 셋리스트를 보여준다.

### 5.6 후순위 — 하이라이트 찾기

문제: 대상 팀이 20~30개, 곡당 3~5분이면 전부 듣는 데 1.5~2시간이다. 지금은 팀 설명에 "1:23 하이라이트 들어주세요"라고 글로 적어 홍보한다. 글은 플레이어와 안 이어져서 작성자가 손으로 찾아가야 한다.

**1단계 — 파형 플레이어** (스키마 변경 없음, 프론트만)

- 피드백 페이지의 플레이어 진행 바를 **소리 크기 파형**으로 그린다 (SoundCloud 방식). 작성자가 파형을 보고 세게 치는 구간(대개 후렴·솔로)을 눌러 바로 간다. 팀이 뭘 적어두지 않아도 된다.
- 구현은 브라우저에서 음원을 디코드해 그린다 (`wavesurfer.js` 같은 표준 라이브러리). 열어 둔 곡 하나만 디코드하므로 목록 전체를 미리 받지 않는다. 서버 쪽 파형 계산(ffmpeg 등)은 두지 않는다.
- 한계: 파형은 "큰 소리"를 보여줄 뿐 "들어주길 바라는 구간"이 아니다. 조용한 파트가 하이라이트인 곡, 압축이 센 믹스에선 덜 유용하다.

**2단계 — 팀 지정 구간** (1단계 뒤에도 팀 설명에 "mm:ss" 홍보가 계속 보이면)

- `Team.highlightStartSec Int?`, `Team.highlightEndSec Int?` — 팀장이 파형 위에서 구간을 찍는다. 제출 단계까지 수정 가능, 피드백 단계부터 잠김 (녹음본과 같은 규칙).
- 파형 위에 구간 표시 + "하이라이트부터" 버튼.
- **하이라이트 이어 듣기**: 목록 상단 버튼 하나로 대상 팀의 지정 구간만 차례로 재생. 20곡 × 30초 = 10분. 미지정 팀은 앞 30초.

우선순위: v0.1(5.1~5.5) 배포 뒤. 1단계는 별도 하위 이슈, 2단계는 근거가 생기면 그때 이슈를 만든다. 컬럼도 그때 추가한다.

## 6. 알림

[NotificationType](../../../packages/database/prisma/schema.prisma)에 추가. 발송은 기존 reminder 스케줄러(10분 주기, "오늘 같은 유형 이미 보냈으면 건너뜀" 패턴) 또는 액션 시점 이벤트.

| 유형                 | 언제                                                  | 누구에게            | 눌렀을 때                     |
| -------------------- | ----------------------------------------------------- | ------------------- | ----------------------------- |
| `RECORDING_DEADLINE` | 제출 마감(`feedbackStartAt`) D-3, D-1, 녹음본 없는 팀 | 팀장                | 팀 편집                       |
| `FEEDBACK_STARTED`   | `feedbackStartAt` 도달                                | 대상 팀 소속자 전원 | `/performances/[id]/feedback` |
| `FEEDBACK_DEADLINE`  | `feedbackEndAt` D-1, 그리고 3시간 전. 미완료자만      | 미완료 작성자       | 피드백 페이지                 |
| `FEEDBACK_RESULT`    | 운영진 확정 순간                                      | 공연 팀 소속자 전원 | `/performances/[id]/result`   |

기존 `TEAM_RECRUITMENT_DEADLINE`은 기준을 `endAt` → `recruitEndAt`으로 바꾼다.

## 8. 작성자 판단으로 정한 것

인터뷰·회의에 없어서 내가 정했다. 틀리면 고친다.

- 점수 범위 1~5 (휴대폰에서 누르기 쉬움. z-score라 범위는 결과에 영향 없음)
- 피드백 자격을 **대상 팀** 소속자로 한정 (미제출 팀만의 소속자는 평가받지 않으니 평가도 안 함)
- 팀장도 소속자로 친다 — 자격·본인 팀 제외·분모·가림 전부. 가림 범위에 프로필 API 포함
- 제출 단계 잠금 = 사람에 관한 것 전부, 곡 정보·이름·설명·사진·녹음본은 허용
- 골든 테스트 전제 = 전원 제출 CSV. 스크립트 분모 방식 스위치 없음
- 가림은 비로그인에도 적용 (공연·팀 조회 API가 공개라서)
- 피드백·결과 페이지는 로그인 필수, 공연·팀 페이지는 지금처럼 공개
- 여러 팀에 속한 사람의 미작성 건수는 소속 팀마다 감점에 반영
- 팀원 가림 기간 = 피드백 + 집계 (결과 공개 전까지). 운영진은 예외
- 결과 페이지에서 부원은 본인 팀 점수만, 합불 목록은 전체
- 분모를 "실제 점수 준 사람 수"로 (D2)
- 감점 기본값 0 — 수치 받기 전까지 꺼진 상태로 배포
- 음원만, 영상 제외
- 단계 이름 `LINEUP` (결과 공개 + 셋리스트 구성 기간)

## 9. 빌더에게 맡기는 것

- 음원 용량·형식 상한 (제안: 50MB, mp3/m4a/wav), presigned URL 만료
- 결과 페이지 애니메이션, 드래그 앤 드롭 라이브러리
- reminder 스케줄러에서 "시작 시점 알림"을 10분 창으로 잡는 방법과 중복 방지
- 마이그레이션 순서 (필드 추가 → 백필 → `isPerformanceRecruiting` 교체 → 옛 필드 의미 복원)
- `PUT /teams/:id` 잠금 검증 방식 (필드별 diff vs 녹음본·설명 전용 엔드포인트)
- 테스트 구성 (CSV → Feedback 행 변환 스크립트 — 0점 관례로 소속 역산, 골든 테스트)
- 파형 플레이어(5.6절 1단계)는 v0.1 뒤 별도 하위 이슈로 추가. 2단계는 근거 생기면
- 하위 이슈 재조정: [#892](https://github.com/skku-amang/main/issues/892)~[#897](https://github.com/skku-amang/main/issues/897)을 이 문서에 맞춤
