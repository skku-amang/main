## 1. 배경 / 목적 / 핵심 페인

### 1.1 현황

공연 팀 선정을 위한 녹음본 피드백를 **구글폼**으로 진행 중. 한 공연 신청 30~50팀, 채택 10~20팀 (1팀당 1곡 = 1녹음본).

### 1.2 4가지 구조적 페인

| # | 페인 | 본질 |
|---|---|---|
| 1 | 클릭 지옥 | 피드백 도중 끊기면 처음부터. 한 피드백 작성자당 평균 87~147개 항목 입력 (29~49팀 × 3항목). |
| 2 | 데이터 오염 | 팀원·친한 사람 녹음본 만점 몰빵, 스케일 일관성 부재, 의도적 왜곡. |
| 3 | Z점수 수작업 | 피드백 작성자별 후함/박함 보정을 운영진이 엑셀에서 손계산. |
| 4 | 인지 부하 | 30~50개 녹음본 비교 피드백 — 자기 페이스 분산, 진행률 가시화 부재. |

> **구조적 한계**: 페인 1·3은 구글폼의 도구적 한계. 페인 2·4는 도구로 일부 완화 가능하나 운영 정책과 결합 필요.

### 1.3 목적

- (1차) 아망 한 공연 운영 — 4가지 페인 v1 스코프(4장) 기준으로 해소.
- (2차) **타 동아리 SaaS 영업 마차** — 일반화된 질문지 모델·peer review 메커니즘으로 횡전개. 댄스·합창·학회 등 적용 가능.
- (NSM) 한 공연 피드백 완료율 ≥ 95% (Pay-to-vote 동작 검증).

### 1.4 비목표 (Out of Scope)

- 곡 연주 순서 결정 (별개 메커니즘, 본 시스템과 분리).
- 공연 당일 운영 (티켓·좌석·녹화 — 별개 시스템).
- 사용자 SSO·결제 — 향후 SaaS화 단계의 별도 결정.
- **외부 알림 시스템 (이메일·푸시·SMS·카카오톡 등)** — 별도 이슈로 분리. 본 spec은 in-app 표시만 다룸. (참고: Slack은 개발팀 내부 도구이므로 사용자 알림 채널에서 제외.)

### 1.5 용어 정의 (도메인 어휘)

본 명세에서 자주 혼동되는 개념을 명시 분리:

| 용어 | 의미 | 예시 / 데이터 위치 |
|---|---|---|
| **곡 (Song)** | 팀이 무대에 연주하기로 선정한 음악 자체. **메타데이터**로 표현 — 제목, 원곡 아티스트, 장르, 길이 등. | `Team.songName`, `Team.songArtist`. RECRUITING 단계에 신청. |
| **녹음본 (Recording)** | 팀이 피드백용으로 제출한 **음원·영상 파일**. 팀이 그 곡을 연주한 결과물. **피드백의 직접 대상물**. | MinIO 파일. SUBMISSION 단계에 업로드. 기존 운영에서는 `Team.songYoutubeVideoUrl`로 표현 (마이그레이션 대상). |
| **피드백 (Feedback)** | 피드백 작성자가 한 녹음본에 대해 입력하는 데이터 = 점수(scoring=true 항목의 numeric 값) + 코멘트(scoring=false 텍스트 항목). 점수는 채택 결정에, 코멘트는 작성팀 in-app 전달에 사용. | `Evaluation` + `Answer` 엔티티 (5장). EVALUATION 상태에서 입력. |
| **피드백 작성자 (Reviewer)** | 본 시스템에서 피드백을 입력하는 사람. 본인 팀 외 모든 신청 팀의 녹음본에 대해 입력 의무 (Pay-to-vote). | `Evaluation.evaluator_id` → `User.id`. |

> 도메인 어휘 사용 원칙:
> - 피드백 대상·파일 처리 맥락 = **녹음본**
> - 메타데이터·운영 맥락 = **곡**
> - 입력 행위·데이터·사람 = **피드백 / 피드백 작성자** (시스템 이름 일관성)
> - 상태 머신의 enum 값은 영문(`EVALUATION` 등) 유지 — 코드 식별자.

## 2. 사용자 역할

한 사람이 **여러 역할을 동시에 가질 수 있음**. 시스템 권한은 역할 단위가 아닌 **(사용자, 공연, 팀) 컨텍스트 단위**로 판정.

| 역할 | 권한 |
|---|---|
| 운영진 | 공연 셋업, 질문지 빌더, 채택 결정, 운영진 대시보드 열람. |
| 팀 리더 | 팀 결성 + 팀원 초대, 녹음본 업로드·변경 (RECRUITING/SUBMISSION 상태 한정). |
| 팀원 | 본인 팀 합류·탈퇴 (RECRUITING 한정), 본인 팀 곡 정보 열람. |
| 피드백 작성자 | 본인 팀 제외 모든 신청팀 피드백 (EVALUATION 상태 한정). 본인 팀의 진척률 위젯 열람. |

> 대부분의 동아리원은 **팀원 + 피드백 작성자**를 동시에 가짐 (Pay-to-vote의 전제).

## 3. 공연(Performance) 라이프사이클 (State Machine)

> **Terminology 정렬**: AMANG 코드베이스에 이미 `Performance` 엔티티 존재 ([packages/database/prisma/schema.prisma:96-112](../../../../packages/database/prisma/schema.prisma#L96-L112)). 본 명세는 "공연" = `Performance` 엔티티로 통일. 한 공연이 곧 한 피드백 라이프사이클의 단위.

### 3.1 상태 전이

```
PREPARING → RECRUITING → SUBMISSION → EVALUATION 🔒 → DECISION → DONE
```

| 상태 | 의미 | 권장 진입 모드 |
|---|---|---|
| PREPARING | 운영진이 공연 메타·질문지 빌더 작업 | **Manual** — 운영진이 새 공연 생성 |
| RECRUITING | 팀 결성·합류·곡 신청 받는 기간 | **Manual 우세** — 빌더 작업 완료 후 운영진 선언. 자동은 reminder만. |
| SUBMISSION | 팀 구성 마감, 녹음본 업로드만 가능 (곡 메타 변경 차단) | **Auto + Manual 단축** — 모집 마감일 자동, 조기 마감은 수동 |
| EVALUATION 🔒 | **피드백 진행 — 모든 팀 쓰기 freeze** | **Auto + 가드** — 녹음본 업로드 마감일 도달 + 모든 팀 녹음본 업로드 완료 가드 통과 시. 가드 실패 시 운영진 결정 대기. |
| DECISION | 운영진이 채택 결정 | **Auto + Manual 단축/연장** — 피드백 마감일 자동, 피드백 연장 가능 |
| DONE | 코멘트 작성팀 in-app 적재 + 정리 | **Manual 강제** — 인간 채택 결정, 자동 불가 |

> 역행 전이(예: EVALUATION → SUBMISSION 되돌리기)는 v0.1에서 미허용. **[오픈 결정 — yungs]** 운영 사고 발생 시 운영진이 강제 되돌리는 절차 필요한지.

### 3.2 상태별 허용 작업 매트릭스

| 작업 | PREPARING | RECRUITING | SUBMISSION | EVALUATION 🔒 | DECISION | DONE |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 공연 메타·질문지 수정 | ✅ | ⚠️* | ❌ | ❌ | ❌ | ❌ |
| 팀 결성 | ❌ | ✅ | ❌ | ❌ | ❌ | ❌ |
| 팀 합류·탈퇴 | ❌ | ✅ | ⚠️* | ❌ | ❌ | ❌ |
| 녹음본 업로드·변경 | ❌ | ✅ | ✅ | ❌ | ❌ | ❌ |
| 피드백 입력 (점수+코멘트) | ❌ | ❌ | ❌ | ✅ | ❌ | ❌ |
| 점수 집계·Z점수 계산 | — | — | — | 실시간 | 자동(진입 시) | 읽기 |
| 운영진 채택 결정 | ❌ | ❌ | ❌ | ❌ | ✅ | ❌ |
| 코멘트 작성팀 전달 (in-app) | ❌ | ❌ | ❌ | ❌ | ❌ | 자동 |
| 피드백 결과 열람 (운영진) | — | — | — | 진척률만 | 전체 | 전체 |

> ⚠️* **[오픈 결정 — yungs]**:
> - 공연 메타 수정의 RECRUITING 후행 허용 범위 (예: 일정 조정만 OK?)
> - 팀 탈퇴의 SUBMISSION 단계 허용 여부 (강의 일정 충돌 등 불가피한 경우).

### 3.3 무결성 정책

- **EVALUATION 진입 시 freeze**: 팀 구성·곡 메타·녹음본 모두 read-only.
- 피드백 데이터는 EVALUATION 상태에서만 write 가능.
- **[오픈 결정 — 남승민]** freeze 가드 구현 위치: app-level guard만 / DB-level constraint도 추가. 표준은 둘 다 (앱은 친절한 에러 메시지, DB는 우회 차단 안전망).

### 3.4 상태 전이 메커니즘

#### 3.4.1 주체 (Authority) 및 합의 게이트

##### 권한 root

- 수동 전이의 권한 root = `User.isAdmin = true` (기존 컬럼 활용, [packages/database/prisma/schema.prisma:46](../../../../packages/database/prisma/schema.prisma#L46)).
- v0.1 정책: **isAdmin 1명의 액션으로 충분** — 단일 admin 레이어. SaaS 초기의 클래식 패턴 (Stripe·GitHub 등도 초기엔 `is_owner` 단일 모델로 시작).

##### 합의 게이트 (Consensus Gate) — DECISION → DONE 등 critical 전이의 안전판

| 시점 | 정책 |
|---|---|
| **이상** | 회장(president) 1명만 확정 가능. 다른 운영진은 제안·검토만. |
| **현실 (v0.1)** | 시스템에 회장 식별 모델 없음 → 운영진 누구나 확정 가능. **운영 컨벤션**으로만 "회장이 마지막 버튼" 운영. |
| **안전판 (v0.1)** | (a) 감사 로그(`PerformanceTransition`)에 actor_id 기록. (b) 운영진 대시보드(in-app)에 전이 이력·현재 상태 가시화. (c) 트랜스페어런시 — 사후 추적·이의제기 가능. |
| **중기 (v2)** | 회장 역할 명시적 모델링 — **별도 role 컬럼 신설** 또는 RBAC 도입. 사용자 베이스 확장(타 동아리 SaaS 영업) 시점에 맞춰 진화. |

> **참고**: AMANG schema의 `Generation.leader` 필드 ([schema.prisma:64-71](../../../../packages/database/prisma/schema.prisma#L64-L71))는 **기장(기수 대표) 타이틀 역할만** — 회장과 완전 독립이며 별도 권한 없음. 따라서 합의 게이트 권한자 식별에는 활용 불가, 별도 role 모델 필요.
>
> **[오픈 결정 — 남승민]** 권한 모델 일반화 — 현재 `isAdmin: boolean`은 단일 계층. SaaS 추상화 시 "일반 운영진 / 부회장 / 회장" 같은 다단 enum 또는 RBAC 필요할 수 있음.

#### 3.4.2 방법 (Trigger Policy)

전이 모드 = `manual` / `auto` / `mix` enum. 단계별 정책:

| 전이 | 권장 모드 | 자동 트리거 시그널 | 수동 액션 위치 |
|---|---|---|---|
| PREPARING → RECRUITING | manual 우세 | (없음). recruitingStartAt 도달 시 운영진에게 reminder만. | 운영진 대시보드 "모집 시작" 버튼 |
| RECRUITING → SUBMISSION | mix | recruitingEndAt 도달 시 자동. | "모집 조기 마감" 버튼 |
| SUBMISSION → EVALUATION | auto + 가드 | submissionEndAt 도달 + 모든 팀 녹음본 업로드 완료. 가드 미충족 시 운영진에게 결정 요청. | "피드백 시작" / "미업로드 팀 배제 후 시작" 버튼 |
| EVALUATION → DECISION | mix | evaluationEndAt 도달 시 자동. | "피드백 연장" / "조기 마감" 버튼 |
| DECISION → DONE | manual 강제 | (없음) | "채택 결정 확정" 버튼 (합의 게이트 옵션 적용 가능) |

> **[오픈 결정 — yungs/손장수]** 자동 트리거 cron 워커 위치 — NestJS `@Cron` decorator / 별도 worker 컨테이너 / k8s CronJob. 남승민·손장수 협의.
> **[오픈 결정 — yungs]** 마감 시각이 야간일 때 자동 트리거 시점 — 정시 vs 다음 영업 시작 시각으로 미루기.

#### 3.4.3 가드 (Precondition)

각 전이는 데이터 무결성 검증 통과해야 진행. 실패 시 친절한 에러 + 어떤 항목 부족한지 명시.

| 전이 | 가드 |
|---|---|
| PREPARING → RECRUITING | 질문지 빌더에 최소 1개 scoring=true 질문 존재. 공연 메타 필수 필드(name, recruitingEndAt 등) 채워짐. |
| RECRUITING → SUBMISSION | 모든 Team에 leader 존재 (Prisma 강제 + 추가 검증). 빈 팀(멤버 < 2) 자동 정리 또는 운영진 결정. |
| SUBMISSION → EVALUATION | 모든 Team에 녹음본 파일 업로드 완료. 미업로드 팀이 있으면 운영진 결정 대기 (배제 vs 연장). |
| EVALUATION → DECISION | (없음) — 피드백 미완료자가 있어도 진행 가능. Pay-to-vote 페널티는 점수 산출 시 적용. |
| DECISION → DONE | 모든 Team에 채택/탈락 결정 기록. |

#### 3.4.4 부수효과 (Side Effects)

전이 시 시스템 내부 작업으로 실행. **외부 알림 발송(이메일·푸시 등)은 본 spec out of scope** — 별도 이슈에서 다룸.

| 전이 | 부수효과 (시스템 내부) |
|---|---|
| PREPARING → RECRUITING | (in-app) 동아리원 홈에 "모집 중" 배너 노출 |
| RECRUITING → SUBMISSION | (in-app) 팀 리더 대시보드에 "녹음본 업로드 마감 임박" 표시 |
| SUBMISSION → EVALUATION | freeze 적용. (in-app) 피드백 작성자 홈에 "피드백 진행 중" 표시 |
| EVALUATION → DECISION | 점수 자동 산출 워커 트리거 (Z점수·가중합) |
| DECISION → DONE | 코멘트 작성팀 in-app 페이지에 코멘트 도달, 운영진 대시보드에 공연 종료 표시 |

> **[오픈 결정 — 남승민]** 점수 산출 워커의 트랜잭션 경계 — 상태 변경과 워커 트리거를 동일 트랜잭션 / outbox 패턴 / 별도 워커. 워커 실패 시 상태 롤백 여부 결정 필요.
>
> **외부 알림 발송 연동 지점**: 별도 알림 시스템 이슈에서 본 표의 각 전이 row를 외부 알림 트리거로 활용 가능 (이벤트·webhook 모델링 시점에 결합).

#### 3.4.5 감사 로그 (Audit Trail)

- 신규 엔티티 `PerformanceTransition` (5.1 보강) — `from_status`, `to_status`, `actor_id`(자동 시 NULL), `trigger`(manual/auto), `reason`(텍스트, 가드 우회 시 사유), `at`.
- 운영 사고 추적·디버깅 필수. v0.1부터 포함.

#### 3.4.6 멱등성 (Idempotency)

- 같은 `from_status`에서 같은 `to_status`로 중복 시도 시 no-op 응답 (이미 전이됨, 200 + 현재 상태).
- 부수효과는 한 번만. **[오픈 결정 — 남승민]** outbox/transactional pattern.

#### 3.4.7 역행 전이 (Rollback)

- v0.1 미허용. 사고 시 운영진이 DB 직접 수정 + 감사 로그 사후 기입.
- **[오픈 결정 — yungs]** v2 운영진용 강제 되돌리기 UI — 운영 사고 빈도 데이터 보고 결정.

## 4. 핵심 기능 명세

### 4.1 공연 관리 (운영진)

- 공연 생성: 이름, 시작일·마감일, 단계별 일정 (PREPARING ~ DONE 각 단계 시작·종료).
- 공연 목록·상태 조회.
- 공연 종료(아카이브): DONE 후 운영진이 명시적 종료 → 데이터 read-only 보존.
- **[오픈 결정 — yungs]** 공연 복제 — 이전 공연 질문지·일정을 새 공연으로 복제 가능 여부 (재사용성↑).

### 4.2 질문지 빌더 (운영진) ★ 일반화 핵심

본 시스템의 **SaaS 일반화 무기**. 질문 = 피드백 항목.

#### 4.2.1 질문 정의

각 질문은 다음 속성을 가짐:

| 속성 | 의미 | 예시 |
|---|---|---|
| 라벨 | 피드백 작성자에게 보일 질문 텍스트 | "이 팀의 개인 실력은?" |
| 타입 | 입력 형식 | numeric_scale / text / multi_choice |
| scale 범위 | numeric_scale 한정 — min·max·step | 1~5 step 1 |
| scoring 플래그 | 점수 산출에 포함 vs 제외 | true (실력) / false (자유 코멘트) |
| 가중치 | 점수 산출 시 가중합 계수 | 0.4 (실력) / 0.4 (팀 합) / 0.2 (선호도) |
| 필수 여부 | 피드백 작성자 입력 의무 | true / false |
| 정렬 순서 | 피드백 화면 렌더링 순서 | 1, 2, 3... |

> **[오픈 결정 — yungs]** 질문 타입 enum 확정. v0.1 제안: `numeric_scale` + `text`. (multi_choice·yes_no는 v2 검토.)
> **[오픈 결정 — yungs]** 가중치 합 = 1.0 강제 vs 자유. 자유 시 정규화 자동.
> **[오픈 결정 — yungs]** scale 범위는 공연 단위 통일 vs 질문별 가변.

#### 4.2.2 빌더 UX (운영진 대상)

- 질문 추가/삭제/순서 변경 (드래그 앤 드롭).
- 질문 미리보기 — 피드백 작성자 시점 화면 시뮬레이션.
- 질문지 템플릿 라이브러리 (v2): 다른 공연·동아리 템플릿 가져오기.
- 빌더 작업은 **PREPARING 상태에서만 자유 수정 가능**. RECRUITING 진입 후엔 [오픈 결정 — yungs] 한정 항목만 수정.

#### 4.2.3 코멘트 채널 = 질문의 한 형태

자유 코멘트는 **별도 기능이 아니라 `type=text, scoring=false` 질문**으로 일반화. 운영진이 빌더에서 "팀에게 전달할 코멘트" 항목을 추가하면 DONE 진입 시 자동으로 작성팀 in-app 페이지에 적재.

> **[오픈 결정 — yungs]** 코멘트 익명성: 익명 / 실명 / 작성팀에게는 익명·운영진엔 실명 (학술 리뷰 패턴). v0.1 제안: 익명.
> **[오픈 결정 — yungs]** 코멘트 in-app 노출 시점: DONE 진입 시 일괄 / 개별 도착 시 즉시. v0.1 제안: 일괄.

- **업로드**: 팀 리더가 RECRUITING 또는 SUBMISSION 상태에서 업로드 (presigned URL).
- **재생**: 피드백 작성자만 EVALUATION 상태에서 재생 가능 (signed URL, 유효기간 짧게).
- **포맷**: mp3 + (옵션) mp4 영상. 파일 크기 한도 [오픈 결정 — yungs/손장수].
- **마이그레이션**: 본 시스템 첫 공연부터 신규 녹음본은 자체 스토리지. 과거 공연의 유튜브 비공개 링크는 그대로 보존 (변환 X).
- **[오픈 결정 — yungs]** 저작권·사적 사용 명시 — 업로드 시 동의 체크박스 필요. 동아리 내부 피드백 한정 명문화.

### 4.5 피드백 화면 (피드백 작성자)

핵심 UX. **비동기 셀프페이스**.

- 피드백 대상 = 본인 팀 제외 모든 신청 팀의 녹음본 (n-1개).
- 한 화면당 한 녹음본 — 페이지네이션 또는 무한 스크롤 [오픈 결정 — yungs+수연].
- 녹음본 재생 컨트롤 (재생/일시정지/탐색).
- 질문지 빌더에서 운영진이 정의한 질문들을 동적 렌더링.
- **autosave**: 모든 입력은 즉시 서버 저장 (debounce 가능). 페이지 이탈·브라우저 종료에도 진척 보존.
- 진척 복원: 재방문 시 마지막 위치·입력값 복원.
- 모바일·데스크톱 둘 다 — 피드백 부하(아망 운영 가설 = 신청 30~50팀 × 운영진 정의 항목 수, 일반화 후 가변)를 며칠에 걸쳐 분산해야 하므로 모바일 사용 빈번.

> **[오픈 결정 — 수연]** 화면 구조 (한 녹음본 전체 화면 vs 녹음본 리스트 + 사이드 패널).
> **[오픈 결정 — yungs]** 피드백 순서 — 운영진 지정 / 무작위 / 피드백 작성자 선택. 무작위가 채택 결정 공정성에 유리하나, 피드백 작성자 자율 선택이 self-paced UX에 유리.

### 4.6 피드백 진척률 위젯

Pay-to-vote 사회 압력 가시화.

- 본인 팀 진척률 카드: "우리 팀 N명 중 M명 피드백 완료, K명 미완료 (X% 완료)".
- 미완료 멤버는 [오픈 결정 — yungs] 익명 / 실명 노출.
- 본인 피드백 진척률: "29팀 중 17팀 피드백 완료".
- D-day 카운터.

> **[오픈 결정 — yungs]** Pay-to-vote 강제 단위:
> - **(a) 팀 단위 100%** — 팀 멤버 전원 완료해야 본인 팀 채택 후보 인정. 가혹하나 가장 강력.
> - **(b) 개인 단위** — 미참여자만 본인 피드백 점수 무효 처리. 팀 전체 페널티 없음.
> - **(c) 비례 가중** — 팀 멤버 피드백 완료율 비례로 본인 팀 점수 보정.
>
> v0.1 제안: **(a) 팀 단위** — 사용자 결정에서 "미참여 시 본인 팀 탈락 위험/탈락" 선택과 정합. 다만 4명 팀에 1명 미완료 시 가혹할 수 있어 yungs/회의에서 (c) 비례 가중으로 완화 검토 권장.

### 4.7 알림 시스템 — 보류 (별도 이슈)

> **본 spec out of scope.** 외부 알림 발송(이메일·푸시·SMS·카카오톡 등)은 별도 이슈로 분리 — 사용자 알림 채널 결정·인프라·UX 모두 별개 영역. Slack은 개발팀 내부 도구이므로 사용자 알림 채널에서 제외.
>
> **본 spec 안에서 처리하는 범위**: in-app 표시 (홈 배너, 대시보드 카운터, 코멘트 도착 페이지 등). 외부 알림 시스템과의 연동은 향후 이슈에서 본 spec의 상태 전이 부수효과(3.4.4)를 트리거 시그널로 활용.
>
> **[오픈 결정 — yungs/손장수]** 별도 이슈 등록 시점·우선순위. 본 spec 구현 후 별도 마일스톤으로 진행 권장.

### 4.8 점수 산출

- **EVALUATION 실시간**: 입력될 때마다 진척률 + 임시 평균 갱신 (운영진은 진척률만 열람).
- **DECISION 진입 시 자동 계산**:
  1. scoring=true 질문만 추출.
  2. **피드백 작성자별 Z점수 정규화** — 각 피드백 작성자의 입력 분포(평균·표준편차)로 정규화하여 후함/박함 보정.
  3. 정규화된 점수 × 가중치 → 팀별 가중합.
- 운영진이 빌더(4.2)에서 정의한 **가중치가 항목별 영향 조절을 일반화** 처리. 시스템 차원의 자동 "객관/주관 분리"는 v1에 없음 — 운영진이 가중치 0으로 두면 점수 산출 제외. 자유 코멘트는 scoring=false 플래그로 자연 제외.
- **[오픈 결정 — yungs]** 운영진에게 항목 `category` 메타(객관/주관/etc.) 부여 권한 줄지. v2에서 카테고리별 분리 정규화 옵션 검토.
- 결과 = 팀별 최종 점수 + Z점수 산출 근거 (운영진이 검증 가능).
- **이상 피드백 탐지**: 모든 녹음본에 동일 점수, 본인 팀에 만점 등 패턴 플래그 → 운영진 검토 큐.

> **[오픈 결정 — 남승민]** 점수 계산을 SQL/Postgres function으로 / Node 애플리케이션 레이어로 / 별도 워커로. 데이터 양 작아서 셋 다 가능.

### 4.9 운영진 대시보드 (DECISION 상태)

- 팀별 최종 점수 표 (정렬·필터 가능).
- 채택/탈락 토글 (운영진 결정 기록).
- 이상 피드백 탐지 큐 — 검토 후 해당 피드백 무효 처리 또는 그대로.
- 채택 결정 확정 → DONE 전이 + 코멘트가 작성팀 in-app 페이지에 적재.
- **[오픈 결정 — yungs]** 채택 결정의 의사결정 룰 — 점수 cutoff / 점수 + 운영진 토론 / 자유 재량.

### 4.10 코멘트 채널 — 작성팀 전달

- DONE 진입 시 자동 적재.
- **앱 내 페이지** (v1 범위): 본인 팀에게 도착한 코멘트 리스트 (4.2.3의 익명/실명 정책 적용). 팀 리더·팀원이 로그인 후 확인.
- **외부 알림 발송** (v1 out of scope): 별도 알림 시스템 이슈에서 다룸 (4.7 참조). 본 spec 구현 후 연동.
- **[오픈 결정 — yungs]** 코멘트 reply / 운영진 모더레이션 / 욕설 필터.

### 4.11 이상 피드백 탐지 — AX 차원

손장수님 영역(AX = AI Experience)의 v1 진입 지점. **v1은 통계적(rule-based) anomaly 탐지로 한정**.

#### 4.11.1 v1 범위 — 통계적 이상 탐지 (rule-based)

피드백 데이터의 분포·패턴을 기반으로 사전 정의된 룰로 이상 플래그. 학습 모델 없음, 단순하고 명확.

| 룰 | 의미 | 운영진 액션 |
|---|---|---|
| `all_same_score` | 한 피드백 작성자가 모든 녹음본에 동일 점수 부여 | 검토 후 무효 처리 또는 그대로 |
| `zero_variance` | 한 피드백 작성자의 점수 분산 = 0 (성의 없음) | 검토 |
| `own_team_max` (보호) | 본인 팀에 만점 — 시스템적으로 본인 팀 평가 차단되어 있어야 하지만 우회 시 탐지 | 검증 |
| `outlier_z` | 한 피드백 작성자의 점수가 다른 작성자들 대비 outlier (z > 임계치) | 검토 |
| `incomplete_to_total_skew` | 미완료 항목 비율 + 완료 항목 점수 편향 결합 패턴 | 검토 |

> **[오픈 결정 — 손장수]** 룰 임계치(예: outlier_z의 z 임계 2.0/2.5/3.0). 운영 데이터 수집 후 튜닝.
> **[오픈 결정 — 손장수]** 룰 추가/수정 메커니즘 — 코드 하드코딩 / 운영진 설정 가능 (v2 고려).

#### 4.11.2 v2+로 연기

다음은 **v1 out of scope**. 데이터 누적·운영 검증 후 별도 이슈로 진행.

- **ML anomaly 탐지** — 피드백 작성자 이력 학습 후 outlier 점수 패턴.
- **코멘트 요약 (LLM)** — 작성팀에게 전달 전 LLM 요약·sentiment 정리.
- **녹음본 그룹핑·청취 순서 추천 (LLM/임베딩)** — 비교 피드백 부하 감소.

> AX 차원 v2+ 진화는 **한 시즌 운영 데이터 분석 후 결정**. 데이터 없이 ML 도입은 over-engineering.

## 5. 데이터 모델 개요 (남승민 영역 — 큰 그림만)

> **이 섹션은 의도적으로 간략**합니다. 정식 ERD는 남승민 작성. 본 섹션은 빈칸과 핵심 엔티티 후보만.

### 5.1 핵심 엔티티 (가설)

> **기존 엔티티 활용**: AMANG 코드베이스에 `Performance`, `Team`, `User` 등 기반 엔티티 존재. 본 시스템은 (a) 기존 엔티티에 컬럼 추가, (b) 신규 피드백 도메인 엔티티 추가로 구성.

#### 5.1.1 기존 엔티티 보강 (마이그레이션)

| 엔티티 | 추가 컬럼 | 비고 |
|---|---|---|
| `Performance` | `status` (enum: PREPARING~DONE), `recruitingStartAt`, `recruitingEndAt`, `submissionEndAt`, `evaluationEndAt`, `decisionEndAt` | 기존 `startAt/endAt`은 공연 본 무대 일시. 라이프사이클 phase별 마감은 별도. |
| `Team` | (없음 또는) `recordingFileKey` (MinIO 녹음본 파일) — 또는 별도 Recording 엔티티 [오픈 결정 — 남승민] | 기존 `songYoutubeVideoUrl`은 과거 공연용으로 그대로 보존 (변환 X). |

#### 5.1.2 신규 엔티티 (피드백 도메인)

| 엔티티 | 핵심 속성 | 관계 |
|---|---|---|
| Questionnaire | performance_id | has many Question |
| Question | label, type, scale_range, scoring, weight, required, order | belongs to Questionnaire |
| Evaluation | evaluator_id, target_team_id, performance_id, status (in_progress/done) | has many Answer |
| Answer | evaluation_id, question_id, value (numeric or text) | |
| Score | performance_id, team_id, raw_total, z_normalized_total, computed_at | |
| AnomalyFlag | evaluation_id, rule, severity, status (pending/resolved) | |
| **PerformanceTransition** | performance_id, from_status, to_status, actor_id (nullable), trigger (manual/auto), reason, at | 감사 로그. 3.4.5 참조. |

### 5.2 핵심 결정 영역 (남승민)

- 공연 상태 freeze 가드: app-level / DB-level / 둘 다.
- Z점수·가중합 계산: SQL function / 앱 레이어 / 워커.
- Evaluation 자동 저장 트랜잭션 단위 (Answer 단위 vs 화면 단위).
- 녹음본 파일 권한 — signed URL 만료, 피드백 작성자 정책 매핑.
- 일반화된 Question 모델의 polymorphism — 단일 테이블 + value JSON / 타입별 별도 테이블.
- Questionnaire 엔티티 분리 vs Performance 직속 — 공연당 질문지 1개 가정 시 Questionnaire 생략 가능, 다중 가정 시 분리. v0.1엔 엔티티 분리 가정.

## 6. 비기능 요구사항 (NFR)

### 6.1 성능 / 부하

- 한 피드백 작성자 입력 항목 수 = (신청팀 - 1) × 운영진 정의 질문 수. 아망 가설(신청 30~50, 질문 3~5) 기준 ~90~250항목. 일반화로 가변.
- autosave 빈도는 1입력당 즉시 (debounce 200~500ms).
- 동시 피드백 작성자 = 최대 신청팀 멤버 합 (보통 100~200명). 한 공연 동안 분산되므로 동시성은 낮음.
- 점수 산출은 DECISION 진입 시 1회. 비동기 작업 OK (UI에서 진행률 표시).

### 6.2 가용성

- 피드백 기간 중 다운타임 = critical. AMANG 클러스터 운영 SLO 적용.
- MinIO presigned URL 만료 적정 — 녹음본 재생 끊기지 않을 만큼.

### 6.3 SaaS 추상화

- Question 모델 일반화 (4.2).
- Object storage S3 호환 인터페이스 (4.4).
- Pay-to-vote 강제도(strictness) enum (4.6 — v0.1엔 한 값만 노출, v2 옵션화 대비).
- 공연 라이프사이클 상태 머신 — 동아리별 단계 가감 가능성 [v2 검토].

### 6.4 보안 / 무결성

- 피드백는 EVALUATION 상태에서만, freeze는 둘 다 (앱+DB).
- 녹음본 파일 = 피드백 작성자만 접근. signed URL.
- 익명 코멘트는 작성자 ID 분리 저장 (모더레이션·이상 탐지에는 식별 가능, 작성팀 in-app 전달엔 미노출).

### 6.5 로그·관측 (AMANG 클러스터 표준)

- Sentry 에러 트래킹 (이미 통합).
- Grafana — 피드백 완료율·이상 탐지 발생률 대시보드 [오픈 결정 — 손장수].

## 부록 A. 페이스메이커 초안의 작성 방법론

본 문서는 brainstorming(설계 명확화) 세션의 산출물입니다. 손장수가 yungs 영역(기획·기능명세)에 페이스메이커로 진입한 정당화·운영 모드:

1. **영역 분담 유지**: 본 초안은 "확정"이 아니라 "초안". yungs가 받아 정정·확장하면 v0.2부터 yungs가 SSOT 소유자.
2. **anchoring 함정 회피**: 의도적으로 빈칸·오픈 결정사항을 *명시적으로* 남김. yungs가 "이미 정해져 있네"로 받지 않도록.
3. **영역별 결정 주체 명시**: 각 결정사항에 `[오픈 결정 — {담당}]` 표기. 자기 영역 즉시 식별 가능.
4. **70% 규칙**: 합리적 기본값(default)은 제시하되, 결정 주체가 다른 선택지를 고를 여지 명시.

향후 페이스메이커 운영이 필요한 다른 영역(예: 회의록, 운영 매뉴얼)에도 동일 패턴 적용 가능.
