# ADR-0003: 알림 모바일 도달 채널 — Web Push (PWA), 앱 래핑 없이

**작성일**: 2026-07-21
**상태**: Proposed
**작성자**: JSON (+ Claude Code 협업)
**관련 이슈**: [#347](https://github.com/skku-amang/main/issues/347) (알림 시스템 구축)

## Context

알림 시스템([#347](https://github.com/skku-amang/main/issues/347)) 도입을 준비 중이다. 사용자의 약 80%가 모바일로 접속하고, 그중 약 60%가 iOS다. 알림의 실효성은 모바일 도달률에 달려 있는데, AMANG은 네이티브 앱 없는 웹(Next.js) 서비스라 "모바일 푸시 = 네이티브 앱 전유물"이라는 전제를 검증할 필요가 있었다.

### 주요 사실 (결정 근거)

1. **iOS Safari는 16.4(2023년 3월)부터 Web Push를 지원한다.** 단, **사용자가 "홈 화면에 추가"(PWA 설치)한 경우에만** 수신 가능하다. Safari 탭으로 쓰는 사용자는 푸시를 받을 수 없다. 2026년 현재 iOS 16.4 미만 기기는 사실상 없고, iOS 18.4+의 Declarative Web Push로 수신 안정성도 개선됐다.
2. **Android는 브라우저에서 바로 Web Push가 동작한다** (홈 화면 추가 불필요).
3. **AMANG 사용자는 불특정 다수가 아니라 동아리원이다.** 온보딩·공지에서 "홈 화면 추가" 안내가 가능해, iOS의 설치 마찰을 조직 차원에서 흡수할 수 있다.
4. 브라우저 푸시 권한 프롬프트는 **한 번 거부하면 사이트에서 다시 띄울 수 없다** (사용자가 브라우저 설정에서 직접 풀어야 함). 프롬프트를 띄우는 시점·방식이 opt-in율을 좌우한다.

## Alternatives Considered

### Option A: PWA + Web Push (선택)

- **장점**: 코드베이스 단일 유지 (Next.js 그대로), 비용 0, 스토어 심사 없음, 배포 파이프라인 변화 없음
- **단점**: iOS는 홈 화면 설치자만 수신 — 푸시 커버리지 100% 불가능

### Option B: Capacitor/TWA 앱 래핑 → 네이티브 푸시 (FCM/APNs)

- **장점**: 설치 마찰 최소 (스토어 설치가 곧 푸시 준비), 푸시 커버리지 최대
- **단점**: Apple Developer $99/년, 스토어 심사 대기·리젝 리스크, 네이티브 빌드 파이프라인 추가, 웹·앱 이중 유지보수. 동아리 규모 대비 과투자

### Option C: 푸시 우회 — 카카오 알림톡 / SMS

- **장점**: 설치·권한 자체가 불필요, 도달률 최상
- **단점**: 건당 과금 + 비즈니스 채널 심사(알림톡), 발신번호 등록(SMS). 무료 채널이 가능한 상황에서 고정 운영비 발생

## Decision

**Option A — PWA + Web Push를 모바일 알림 도달 채널로 채택한다.** 사용자가 서로 아는 동아리 조직이라 iOS 설치 마찰을 안내로 흡수할 수 있다는 점, 비용 0과 단일 코드베이스 유지를 우선했고, 그 대가로 "푸시 100% 도달 보장 불가"를 받아들였다.

받아들일 수 있는 이유는 아래 원칙 1이 수신 보장 요구를 구조적으로 제거하기 때문이다.

### 구현 원칙

1. **인앱 알림함이 SSOT, 푸시는 best-effort 트리거.** 알림 자체는 DB(`Notification` 테이블)에 기록되고 인앱 알림함(벨 아이콘)에서 항상 조회 가능하다. Web Push는 "알림함 보러 와라"라는 전달 채널일 뿐, 푸시 미수신이 정보 손실로 이어지지 않는다.
2. **권한 요청은 soft-ask.** 브라우저 프롬프트를 바로 띄우지 않고, 자체 UI로 먼저 의사를 물은 뒤 수락한 사용자에게만 실제 프롬프트를 띄운다 (거부 비가역 완화, 사실 4).
3. **구독 모델**: 사용자 1명 = 기기 N대 = 구독 N개 (`PushSubscription` 테이블, User와 1:N). 발송 시 `410 Gone` 응답을 받은 구독은 삭제하고, service worker에서 `pushsubscriptionchange`를 처리한다.
4. **VAPID 키는 SealedSecrets로 관리.**
5. **full PWA가 아니다.** 오프라인 캐싱 불필요 — `manifest.json` + 푸시 핸들러만 있는 수제 service worker로 최소 구현한다 (`next-pwa`·serwist 미도입).
6. **발송은 NestJS에서 `web-push` 라이브러리로 직접 수행, 큐 미도입.** 동아리 ~100명 규모의 fan-out에 큐는 과투자.

이메일·SMS 등 다른 채널([#347](https://github.com/skku-amang/main/issues/347)에 언급)의 도입 여부는 본 ADR 범위 밖이며 별도로 결정한다.

## Consequences

- **좋은 결과**:
  - 비용 0 (APNs/FCM 경유 Web Push 발송은 무료), 스토어 심사·네이티브 빌드 없이 기존 웹 배포 파이프라인 그대로
  - 알림함 SSOT 구조 덕에 채널(푸시)이 전달에 실패해도 알림은 유실되지 않고, 도달 채널을 나중에 교체·추가하더라도 알림 데이터 모델은 그대로 유지
- **나쁜 결과**:
  - iOS 푸시 커버리지 100% 불가 — 홈 화면 설치 + 권한 허용을 모두 통과한 사용자만 수신. 온보딩 안내로 완화하되 한계는 남음
  - 권한 프롬프트 거부는 사이트에서 복구 불가 — soft-ask로 완화
  - iOS Web Push는 silent push 불가 — 푸시마다 visible notification 강제
  - **VAPID 키 rotation = 기존 구독 전체 무효화** (전 사용자 재구독 필요). 키를 유출 외 사유로 교체하지 않도록 주의
- **중립적 결과**:
  - Web Push는 HTTPS 필수 (localhost만 예외) — 로컬 개발은 가능하나 실기기 검증은 스테이징/프로덕션 URL에서 수행
