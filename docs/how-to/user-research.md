# 부원 의견 모으고 결정까지 잇기

> **For**: 부원 인터뷰를 하거나, 그 결과로 다음 작업을 정하는 사람 (개발자·기획자·인터뷰 대리인·AI).
> **You'll be able to**: 인터뷰를 하고, 기록을 어디에 어떻게 남길지, 그것이 어떻게 로드맵과 GitHub 이슈로 이어지는지 안다.

개발자가 더 이상 주 사용자가 아니기 때문에, "무엇을 만들지"는 개발자의 감이 아니라 **부원의 실제 이야기**에서 시작한다.

> 용어: 이 문서의 "부원 의견"은 인터뷰·대화로 들은 이야기 전체를 말한다. "피드백"은 [용어집](../reference/glossary.md)상 녹음본 피드백 시스템의 이름이라 쓰지 않는다.

## 1. 어디에 무엇을 적나

```text
인터뷰 1회 ──→ 노션 인터뷰 DB (원문, 실명)                [비공개]
                 │ 한 인터뷰에서 인사이트 여러 개
                 ▼
              docs/explanation/research/ (익명 인사이트)   [공개]
                 │ 해결할 문제로 정리
                 ▼
              docs/explanation/roadmap.md (Now/Next/Later)  [공개]
                 │ 해결책 후보
                 ▼
              노션 Task DB (아이디어 + ICE 점수)           [비공개]
                 │ 진행 결정
                 ▼
              GitHub 이슈                                  [공개]
```

| 무엇 | 어디 | 공개 | 한 단위 |
|---|---|---|---|
| 인터뷰 원문 | 노션 인터뷰 DB | ❌ | 인터뷰 1회 = 1행. 원문은 페이지 본문에 |
| 인사이트 | [research/](../explanation/research/) | ✅ | 문제 진술 1개 = 파일 1개 |
| 로드맵 | [roadmap.md](../explanation/roadmap.md) | ✅ | 주제(바뀌어야 할 상태) |
| 아이디어 | 노션 Task DB | ❌ | 해결책 1개 |
| 작업 | GitHub 이슈 | ✅ | 하루 단위 작업 |

원문은 실명과 다른 사람 이야기가 섞여서 비공개로 둔다. 공개하면 부원이 솔직하게 말하지 않는다. 노션 접근은 루트 [AGENTS.md](../../AGENTS.md)의 외부 도구 컨텍스트를 따른다.

## 2. 인터뷰하기

원칙은 *The Mom Test*(Rob Fitzpatrick) 하나다: **미래·의견이 아니라 과거 행동을 묻는다.**

| ❌ 피할 질문 | ✅ 대신 |
|---|---|
| "동방 예약 기능 쓸 거예요?" | "지난번 동방 쓸 때 어떻게 했어요?" |
| "이 기능 있으면 좋겠어요?" | "그때 뭐가 제일 귀찮았어요?" |
| "홈페이지 어때요?" | "이번 주에 홈페이지 몇 번 들어갔어요? 뭐 하러요?" |

- "~하면 좋겠다"는 요청이 나오면 **"그게 없어서 지난번에 어떻게 했어요?"** 로 한 번 더 판다. 지금 쓰는 우회 방법(카톡, 엑셀 등)이 진짜 경쟁 상대다.
- 메모는 아무 데나 빠르게 적는다. 정리는 인터뷰가 끝난 뒤에 한다.
- 설문(구글폼)은 의견만 모이고 정확도가 낮아서 보조로만 쓴다. 사이트 안의 "의견 보내기"로 들어온 내용도 같은 흐름으로 정리한다.

## 3. 인터뷰 정리하기

AI에게 "인터뷰 정리해줘"라고 메모를 넘기면 아래를 한다. 사람이 직접 해도 순서는 같다.

1. **노션 인터뷰 DB에 1행 추가.** 화자·날짜·수집 방법·영역을 채우고, 본문에 원문을 인사이트별로 묶어 적는다. 각 원문 앞에 (행동)/(불편)/(요청)/(긍정)을 붙인다. 실제로 한 일을 말하는 (행동)이 (요청)보다 믿을 만하다.
2. **인사이트 연결.** 기존 [research/](../explanation/research/) 파일과 같은 문제면 그 파일의 근거 수와 관찰을 갱신한다. 새 문제면 새 파일을 만든다 (4절 형식).
3. **아이디어 연결.** 노션 인터뷰 행의 "관련 아이디어"에 Task DB 항목을 연결한다. Task DB의 "근거 수"가 자동으로 늘어나며, 이 숫자를 ICE의 확신도를 매길 때 참고한다.
4. **로드맵 점검.** 근거가 쌓여 우선순위가 바뀌면 [roadmap.md](../explanation/roadmap.md)를 고친다.
5. **이슈 만들기.** 바로 고칠 수 있는 것은 GitHub 이슈로 만들고 `from: user-feedback` 라벨과 인사이트 문서 링크를 붙인다. 노션 링크는 붙이지 않는다 (외부에서 열리지 않음).

## 4. 인사이트 문서 형식

파일명은 `<kebab-case-문제>.md`. 근거가 늘면 같은 파일을 갱신한다.

```markdown
# <문제 진술 한 문장>

> 근거: 인터뷰 N건 · 처음 기록 YYYY-MM-DD · 마지막 갱신 YYYY-MM-DD

## 관찰
- (행동) "들은 말" — 부원 A (일반 부원)

## 해석
## 연결
- 로드맵 주제, 관련 이슈
```

**익명화 규칙**

- 이름 대신 문서 안에서만 쓰는 기호(부원 A, B …)를 쓴다.
- 기수·세션·직책을 **조합해서 한 사람으로 좁혀지면 쓰지 않는다.** "일반 부원 / 팀장 / 운영진 / 신입" 수준까지만 쓴다.
- 다른 부원이나 간부를 평가하는 내용은 옮기지 않는다.

## 5. 하지 않는 것

이슈 템플릿, 노션↔GitHub ID 강제 연결, 인사이트마다 ADR, 날짜가 있는 로드맵, 별도 리서치 도구 도입은 하지 않는다. 필요해지면 그때 가볍게 추가한다.
